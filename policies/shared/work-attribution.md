# 工作归因口径（跨 skill 共享）

**状态：骨架，大量待定义。** 这份文档回答一个问题：*给定一段时间，怎么确定「完成了什么任务、各花了多少工时」？*

它被多个 skill 依赖：
- `tapd-openapi-workflow` —— 决定建哪些任务、写多少工时
- `feishu-doc-access` —— 决定怎么把文档编辑历史转成工作叙述

母版在仓库根 `policies/shared/work-attribution.md`，由 `tools/sync-core.sh` 同步进各 skill 的 `policies/shared/`。**改要改母版。**

---

## 为什么单独一层

归因口径独立于任何一个工具：换掉 TAPD 或换掉飞书，「什么算一个任务」「工时怎么估」都不变。写在任一 skill 里都会变成另一个 skill 的隐性依赖。

## 已确立的部分

- **证据和结论要分开。** 编辑次数、commit 数量是证据，不是工时。任何换算关系都必须显式说明。
- **推断必须标注。** 见各 skill 的 reporting 口径。
- **写入前必须确认。** 归因结果在写进 TAPD 之前要让用户过一遍。工时会被用于考核，错误成本不对称。

## 待定义（TODO）

下面每一条现在都没有答案，遇到时**必须问用户，不要自行假设**。

### 1. 什么算「一个任务」

- 按可验收产出切？按代码模块切？按迭代里的需求切？
- 一个 PR 对应一个任务，还是一个功能对应一个任务（可能含多个 PR）？
- 调研、返工、修 bug 算独立任务还是并入原任务？

### 2. 怎么从代码仓库归纳

- 用什么作为输入：commit message、PR 标题、diff 范围、分支名？
- 一个人同时在多个仓库上推进时怎么合并（每个仓库各自独立成任务，还是按业务归并）？
- 怎么处理没有 commit 的工作（评审、联调、答疑）？
- merge commit、revert、格式化提交怎么排除？

### 3. 工时怎么估

- 有没有可用的客观信号（commit 时间跨度、IDE 时长、日报）？
- 没有客观信号时用什么默认口径，还是一律问用户？
- 一天的总工时是先定总数再分摊，还是逐任务估算后加总？
- 上限和取整规则见 `tapd-openapi-workflow/policies/policy.json` 的 `dailyHoursCap` / `minTimesheetIncrement`。

### 4. 边界情况

- 跨天但不连续的工作怎么落日期？
- 同一天做了多个任务，怎么分配工时？
- 被打断/等待/阻塞的时间算不算，算在哪个任务上？
