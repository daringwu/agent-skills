# 工作归因口径（跨 skill 共享）

**只回答一个问题：** 给定一段时间的痕迹（git 提交、文档编辑历史），归纳出「做了哪些事」——一份带证据的活动清单。

**明确不回答：** 这些事怎么变成 TAPD 任务行、每行填几小时、任务怎么命名。
那些是**记录格式**问题，由记录目标决定，换个系统就全变。见 `tapd-openapi-workflow/policies/`。

划这条线的理由：工时这个概念是 TAPD 造出来的——不用 TAPD 就没人需要估工时。
把它写进共享层，等于把一个工具的字段需求伪装成普适原则。

母版在仓库根 `policies/shared/work-attribution.md`，由 `tools/sync-core.sh` 同步进各 skill。**改要改母版。**

## 输出形态

这一层的产物是活动清单，不是任务表：

```
2026-08-24  接入埋点 SDK          证据: PR #12, commit a1b2c3
2026-08-25  补齐页面事件          证据: PR #15
2026-08-25  参加需求评审          证据: 飞书文档 xxx 于当日被编辑
2026-08-27  修复上报缺失          证据: PR #18
```

下游（TAPD skill）再按它自己的粒度口径把这些行合并成任务、按它的工时口径估算数字。

## 已确立

- **证据和结论要分开。** 编辑次数、commit 数量是证据，不是工时，也不是工作量。任何换算关系都必须显式说明。
- **推断必须标注。** 三种可信度要能区分：直接可见（commit、edit_time）、对比得出（diff、快照比对）、推断（「这段时间大概在做 X」）。
- **写入任何外部系统前必须让用户确认。** 归因结果会流向考核数据，错误成本不对称。

## 待定义（TODO）

遇到时**必须问用户，不要自行假设**。

### 1. 证据来源与优先级

- 用什么当输入：PR 标题、commit message、diff 涉及的文件范围、分支名？
- 冲突时谁优先（PR 标题写得含糊但 diff 很清楚，听谁的）？

### 2. 多仓库

- 同时在多个仓库推进时，每个仓库各自成一条，还是按业务归并？

### 3. 排除规则

- 哪些提交不计入：merge commit、revert、纯格式化、依赖升级、改文档？

### 4. 数据获取方式

- 我能直接读本地/远端仓库，还是由你把范围贴给我？这决定这条流程能否自动化。
