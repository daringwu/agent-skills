# 汇报与推断口径

量化部分见 `policy.json`。这里是需要判断的部分。

## 编辑历史不是工时

飞书的编辑历史能证明「某天有人动过这个文档」，不能证明「那天在这个文档上花了多久」。一次编辑可能是改一个错字，也可能是重写一章。

所以：

- 产出的表格里，「编辑次数」和「工时」必须是两列，不能由前者推后者。
- 需要工时时，走 `policies/shared/work-attribution.md` 的归因流程，并让用户确认。
- 不要用编辑次数给任何东西排序然后称之为「工作量」。

## 推断必须标注来源

一份工作总结通常混了三种可信度：

1. **直接可见**——飞书历史里的 `edit_time` / `editor_ids`、git commit
2. **对比得出**——两个 revision 快照的 diff、代码变更范围
3. **推断**——「这段时间大概在做 X」

产物里必须能看出每一行属于哪一种。最低要求是在表格下方写明数据来源与推断范围。不要把三种混成一句「根据记录整理」。

## 姓名解析的边界

`editor_ids` 是 open_id，不解析就是一串 `ou_...`。解析需要 `contact:user:search`，会扩大通讯录访问面。

默认口径是**不解析**（`policy.json` 的 `resolveEditorNames`）。只有一人协作、id 明显就是用户本人时可以直接标注为本人，但要在产物里说明这是根据 `auth status` 的 `userName` 对应的，不是查通讯录得来的。

## 时间窗口

按日聚合时用 `policy.json` 的 `timezone` 转换后再切天。用 UTC 切天会让晚上 8 点之后的编辑落到第二天，日报会对不上。
